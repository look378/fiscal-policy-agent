# 财政政策 AI 智能体 · 全链路技术解析

> 本文记录项目的设计思路、关键决策、实测数据与踩坑记录。
> 面向面试讲解：每个技术选择都要能回答"为什么这么做"和"不这么做会怎样"。

---

## 一、项目要解决什么

财政政策（政府采购、政府购买服务、专项资金、直达资金）问答有三个实际痛点：

1. **文件分散**：政策散在多个部委网站和 PDF 里，企业办事人员要靠人工翻找
2. **口径严格**：比例、金额、期限写错就是错误咨询（例如"预留份额 30%"错答成"20%"）
3. **无人度量**：上线后没人知道答得准不准，出了问题靠用户投诉发现

对应三个工程目标：**可检索、可溯源、可度量**。

## 二、整体架构

```
政策原文（网页/PDF）
   │ ① 抓取 + 清洗：去导航噪声、按「第X条」结构化
   ▼
知识库（59 条 QA + 5 份政策原文）
   │ ② RAGFlow：文档解析 → 切块 → bge-m3 向量化 → 混合检索
   ▼
问答编排层（自研 FastAPI，约 300 行）
   │ ③ 检索 top_k=8 → 相似度闸门 → 上下文长度控制
   │ ④ 提示词硬约束 → 本地 Ollama 生成 → 引用标注
   ▼
OpenAI 兼容接口（可被 Dify / 任意客户端调用）
   │ ⑤ Prometheus 指标 → Grafana 看板
   │ ⑥ 规则判定 → LLM 归因 → 异常预警
   ▼
Kubernetes（kind）：Deployment / Service / HPA
```

**核心设计决策：RAGFlow 只做"解析+检索"，问答编排自研。**

理由：
- RAGFlow 内置对话流程是黑盒，无法做"引用必须带条款号""数字必须逐字来自上下文"这类硬约束
- 自研编排层能精确控制上下文长度（踩过 Ollama 400 的坑）、拒答策略、指标埋点
- 换模型/换检索后端时，编排层与接口不变

## 三、知识库构建

### 3.1 政策原文获取与清洗

- 从中国政府网抓取 5 份政策原文（HTML → 纯文本）
- 清洗脚本做三件事：
  1. 删网页导航噪声（"首页/登录/字号/打印"等 20+ 类正则）
  2. 从"附件/第X条"开始截取正文
  3. 把每条条款拆成独立行（`### 第X条`），便于后续按条款切块

### 3.2 知识库的双层结构

| 层 | 内容 | 作用 |
|---|---|---|
| QA 层 | 59 条「问题 → 结论/依据/提示」 | 保证高频问题回答质量（结论直接可引用） |
| 原文层 | 5 份政策全文（按条款） | 保证条款级召回与引用溯源 |

**为什么两层都要**：只有 QA 会覆盖不全；只有原文会检索到无关条款、生成端难定位。

### 3.3 切块与向量化

- 切块方式：`naive`（RAGFlow 默认按长度+语义切）
- 向量模型：**bge-m3**（1024 维，中文政策语料效果好，且支持长文本）
- 实测：6 个文档 → **199 个 chunk**，全量索引约 60 秒

### 3.4 一个实际工程问题：embedding 服务怎么来

本机没有可直接用的 embedding 服务，且外网下载模型极慢。做法：
- 用本地已缓存的 bge-m3 权重起一个 **OpenAI 兼容的 embedding 服务**（FastAPI + sentence-transformers）
- RAGFlow 侧注册为 `OpenAI-API-Compatible` 供应商，模型名 `bge-m3@OpenAI-API-Compatible`

> 这一点在面试里是加分项：说明"知道 RAGFlow 的模型接入是解耦的，换 embedding 不用改业务代码"。

## 四、检索层

### 4.1 检索参数与调优

| 参数 | 取值 | 依据 |
|---|---|---|
| top_k | 8 | 5 时"声明函""预留方式"等条款召回不到（badcase #6/#11） |
| 向量权重 | 0.3（关键词权重 0.7） | 政策条款号、"30%"这类精确 token 靠关键词更稳 |
| 相似度阈值 | 0.2 | 低于该值的 chunk 直接丢弃 |

### 4.2 相似度分布分析（决定拒答闸门）

对 49 道评测题统计"最高相似度"：

| 类型 | 典型最高相似度 |
|---|---|
| 可回答问题 | 0.35 ~ 0.49（最低 #2 0.352） |
| 应拒答问题 | #42 0.000 / #48 0.207 / #45 0.285 |

据此设置 **0.33 的低相似度闸门**：正样本零误拒；实测 8 条负样本中 2 条由闸门直接拒答（#42 耗时 0.5s、#48 耗时 0.9s），其余由模型按提示词文本拒答。

> 这是典型的"用数据定阈值"而不是拍脑袋：先跑分布，再看各阈值下的误拒/拦截权衡。

## 五、生成层

### 5.1 为什么用本地模型

- 数据不出内网（财政场景敏感）
- 无 API 成本
- 缺点：deepseek-r1:7b 是**推理模型**，会把 token 花在"思考"上，导致：
  - 慢（端到端约 15~25 秒/题，含检索与外网无关的本地生成）
  - 有时 content 为空（token 全用在思考）→ 加了"空回答放大预算重试"兜底

### 5.2 提示词硬约束（核心）

针对 badcase 提炼出 6 条硬规则：

1. 只依据知识库回答，先结论后依据，必须带政策名+条款号
2. **所有数字必须逐字来自上下文**，上下文没有的数字一律不写
3. **不得把相对时限推算成具体日期**（"30 日内" ≠ "次年 1 月 11 日"）
4. 上下文只有相近条款时，明确说"未找到直接依据"，不许顶替作答
5. 地方标准/未收录文件/个案判断 → 直接说未收录并引导官方渠道
6. 回答控制在 300 字内

### 5.3 上下文长度控制（踩坑）

一次 400 Bad Request 排查：
- 现象：部分问题回答为空
- 定位：Ollama `/api/chat` 返回 400 → 上下文 6034 字超过模型 num_ctx
- 修复：单 chunk 截断 600 字 + 总上下文 3000 字上限 + 显式 `num_ctx=8192`

### 5.4 三层拒答策略

| 层 | 触发条件 | 行为 |
|---|---|---|
| 检索层 | 无命中 / 最高相似度 < 0.33 | 直接返回"知识库中没有查到" |
| 生成层 | 上下文不足（提示词规则 4/5） | 模型输出"未找到直接依据" |
| 兜底层 | 生成失败/超时 | 返回错误提示而非空回答 |

## 六、评测体系（本项目的核心工程价值）

### 6.1 评测集设计

- **49 条**：41 条正样本 + 8 条负样本
- 负样本专门测"会不会乱编"：地方补贴金额、划型数值、投诉时限、竞争性磋商、目录条目、专项资金额度、个案判断、直达资金清单
- 每条都写"期望要点 + 依据条款"，便于判定

### 6.2 评分方案的三次迭代（真实踩坑）

| 版本 | 方案 | 结果 | 问题 |
|---|---|---|---|
| v1 | 关键词命中 | 30.6% | **大量正确答案被判失败**（把"个体工商户在政府采购中视同中小企业"当成一个词去匹配） |
| v2 | LLM 裁判 | 91.7% | **裁判放水**：#12 答"2%—3%"（正确 6%—10%），裁判理由写"数字不符"却判通过 |
| v3 | LLM 裁判 + 数字硬校验 + 负样本确定性判定 | **98.0%**（49 条） | 当前口径，见下 |

**这套迭代本身就是项目的亮点**：说明"评测工具本身也需要被评测"。

### 6.3 当前口径

- 正样本：LLM 裁判判核心要点是否覆盖 + **期望中的关键数字必须出现在回答里**
- 负样本：**确定性判断**（回答是否包含"未找到/没有查到/建议查阅"等拒答标志），不交给 LLM
- 裁判自相矛盾保护：结论"通过"但理由含"不符/错误地/未覆盖"→ 强制改判失败

### 6.4 实测结果

| 指标 | 数值 |
|---|---|
| 总通过率 | 48/49 = **98.0%** |
| 正样本 | 41/41 = 100% |
| 负样本正确拒答 | 7/8 = 87.5% |
| 平均延迟 | 18.2 秒 |

### 6.5 Badcase 归因（写进 `eval/badcase_log.md`）

| # | 现象 | 归因层 | 修复 |
|---|---|---|---|
| 6 | 漏《中小企业声明函》 | 检索 | top_k 5→8，已修复 |
| 11 | 依据错引 | 检索+生成 | top_k + "不许顶替"规则，已修复 |
| 12 | 编造比例 2%—3% | 生成 | 数字逐字引用规则，已修复为 6%—10% |
| 38 | 编造具体日期 | 生成 | "不换算相对时限"规则，已修复 |
| 45 | 竞争性磋商硬答 | 检索→拒答 | 低相似度闸门，已拦截 |
| 49 | 空回答 | 服务层 | 上下文长度控制 + 重试兜底，已修复 |

## 七、监控与预警

### 7.1 指标设计

问答服务暴露 Prometheus 格式指标（counter）：

| 指标 | 含义 | 用法 |
|---|---|---|
| `fiscal_qa_requests_total` | 请求总数 | rate → QPS |
| `fiscal_qa_errors_total` | 错误数 | rate/clamp → 错误率 |
| `fiscal_qa_refused_total` | 拒答数 | 拒答率（知识覆盖度信号） |
| `fiscal_qa_latency_ms_total` | 累计耗时 | 平均延迟 |
| `fiscal_qa_tokens_total` | token 累计 | 生成吞吐 |

### 7.2 Grafana 看板（10 个面板）

QPS / 错误率 / 拒答率 / 平均延迟 / 请求趋势 / 延迟趋势 / token 速率 / 服务存活（`up`）

### 7.3 LLM 异常预警（JD 明确要求）

设计三层：
1. **规则层**：错误率 >10%、拒答率 >40%、平均延迟 >20s、服务 down；同规则冷却期内不重复告警
2. **归因层**：触发后把"指标快照 + 规则说明"交给 LLM，输出「可能原因 / 处置建议 / 是否需人工介入」
3. **出口层**：JSONL 落盘（告警 + 诊断两条记录）+ `/alerts` 查询（`limit` 有界）

> 为什么用 LLM 做归因：阈值告警只告诉你"坏了"，不告诉你"为什么坏"；
> LLM 能结合指标组合给出可执行建议（如"拒答率高 + QPS 正常 → 更可能是检索侧问题而非服务故障"）。

---


### 7.3 内置试用页与 OpenAI 兼容接口（补充）

- `GET /` 提供单文件试用页（HTML/CSS/JS 内联，无 CDN 依赖），仅用于本地演示；
  带 `X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、CSP 与 `Cache-Control: no-store`。
- `POST /v1/chat/completions` 支持 `stream=true`，但当前是**单 chunk 伪流式**：等服务端生成完再一次性推送
  （真流式需要 `generate()` 改流式并延后引用判定）。响应头已加 `Cache-Control: no-cache`、
  `X-Accel-Buffering: no`，避免反代整段缓冲。
- 引用编号解析支持 `[1]`、`【1】`、`[1,2]`、`[1、2]`、`[1-3]`；`（1）` 这类列表编号**不**当作引用。
- 指标口径：`fiscal_qa_refused_total` = 闸门拒答 + 文本拒答；另外单列
  `fiscal_qa_refused_gate_total` / `fiscal_qa_refused_text_total`。

## 八、微调方案（LoRA）

### 8.1 为什么微调、为什么不把知识灌进模型

| 目标 | 手段 |
|---|---|
| 政策知识 | **检索注入**（知识会更新，模型记忆会过期） |
| 输出格式与纪律 | **微调**（结论先行、引用格式、无依据拒答） |

### 8.2 数据构造

- 59 条知识库 QA → 直接转 SFT 样本（输出为结论/依据/提示三段式）
- 10 条库外问题 → 固定拒答模板（训练"什么时候不说"）
- 共 69 条，85/15 切分

### 8.3 训练配置

| 项 | 取值 | 理由 |
|---|---|---|
| 基座 | Qwen2.5-1.5B-Instruct | 8G 显存 bf16 LoRA 可训 |
| 方法 | LoRA r=8/alpha=16，q/k/v/o_proj | 显存友好 |
| 精度 | bf16（不用 QLoRA） | RTX 5060 是 sm_120，bitsandbytes 不稳 |
| loss | 只算答案段（prompt label=-100） | 学"怎么答"而不是"怎么问" |

### 8.4 本机限制（诚实说明）

torch 为 CPU 版、ModelScope 大文件下载 0.18MB/s，本机未实跑训练；脚本与数据可直接在 GPU 机器执行。

## 十、踩坑记录（面试可讲）

1. **Docker Hub 被 DNS 污染**：`registry-1.docker.io` 解析到 `31.13.69.169` → 必须走国内镜像站；镜像站也不稳，需重试
2. **RAGFlow 注册接口有 RSA 加密**：API 注册密码报 `Incorrect padding` → 改用容器内调用服务层函数建账号
3. **RAGFlow Chat API 的 prompt_config 结构**：`prompt_type=simple` 时模板字段是 `system`，塞 `prompt` 会被忽略 → 对话返回模板问候语
4. **Ollama 上下文超限返回 400**：表现为"回答为空"，需看 `error` 字段才定位到
5. **推理模型 token 耗尽**：deepseek-r1 思考过程吃掉全部 num_predict → content 为空
6. **评测工具本身要验证**：关键词打分 30% 假阴性、LLM 裁判放水，都靠交叉校验发现

## 十一、面试问答准备

**Q：为什么用 RAGFlow 而不是自己写解析？**
A：政策文档要处理 PDF/网页/表格/条款结构，RAGFlow 的解析与切块是现成的；我把精力放在它做不好的地方——引用硬约束、拒答策略、评测与监控。

**Q：怎么保证不编造？**
A：三层：检索层相似度闸门（<0.33 直接拒答）、生成层提示词硬约束（数字逐字来自上下文）、评测层负样本专测（8 条库外问题，要求明确拒答）。

**Q：怎么知道答得好不好？**
A：49 条评测集 + LLM 裁判 + 数字硬校验，当前 98.0%；badcase 逐条归因到检索/生成/服务层，修复后回归。

**Q：数据量这么小（69 条）微调有意义吗？**
A：微调目标不是知识而是格式与纪律，小数据足够；且明确说了知识靠检索，不靠模型记忆。

**Q：这个项目最难的部分？**
A：不是搭 RAG，而是"让系统知道自己不知道"——相似度闸门阈值要用分布数据定、负样本要单独设计、拒答词表要复用同一套口径，否则评测和线上会不一致。
