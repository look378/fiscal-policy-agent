## 二、BLOCKER（8 条，必须修才能"可交付"）

### B1. Grafana 看板数据源 uid 不匹配 → 8 个面板全部无数据
- **文件**：`monitoring/grafana/dashboards/fiscal-qa-dashboard.json:12,24,36,48,60,74,86,98` + `monitoring/grafana/provisioning/datasources/prometheus.yml`
- **证据**：providers 里数据源未定义 `uid`，Grafana 自动生成随机 uid；实测该实例数据源 uid = `PBFA97CFB590B2093`，而面板写死 `"uid": "prometheus"`。
- **实测验证**：`GET /api/datasources/uid/prometheus` → **404**；通过 `/api/ds/query` 用该 uid 查询 → 404。
- **影响**：看板能打开但每个面板显示 "Datasource was not found"，监控体系等于不存在。
- **修复**：`provisioning/datasources/prometheus.yml` 增加 `uid: prometheus`。

### B2. 三个服务硬编码只监听 127.0.0.1 → 容器化后完全不可达
- **文件**：`serving/qa_service.py:238`、`serving/embed_server.py:68`、`monitoring/alert_service/alert_service.py:259`
- **证据**：`uvicorn.run(app, host='127.0.0.1', port=args.port)`
- **影响**：
  - `docker run -p 8901:8901` 依然连不上（容器内只监听 loopback）
  - K8s kubelet 从节点侧探测 podIP → readiness/liveness 必然失败 → **Pod 永远 NotReady、反复重启**
  - Prometheus 在容器网络内抓取 → 拿不到数据（当前能通是因为 Docker Desktop 的 vpnkit 转发，属环境侥幸）
- **修复**：加 `--host`（默认 `0.0.0.0`，本机开发也可显式传 `127.0.0.1`），或读 `HOST` 环境变量。

### B3. `serving/Dockerfile` 构建上下文自相矛盾 → 镜像构建不出来
- **文件**：`serving/Dockerfile:4,7-8`
- **证据**：
  - 以仓库根为 context：`COPY requirements.txt /app/requirements.txt` → 失败（根目录无此文件，只有 `serving/requirements.txt`）
  - 以 `serving/` 为 context：`COPY serving/qa_service.py` → 失败（没有 `serving/serving/`）
  - `monitoring/alert_service/Dockerfile:4` 还反向依赖 `serving/requirements.txt`，进一步锁死 context 必须为根
- **修复**：统一以仓库根为 context，`COPY serving/requirements.txt` + `COPY serving/qa_service.py` + 补 `.dockerignore`。

### B4. K8s 清单不可用（三处叠加）
- **文件**：`k8s/manifests.yaml:14-21,53,119`
- **证据与影响**：
  1. **ConfigMap 缺 `RAGFLOW_KEY`**（`qa_service.py:42` 靠它调 RAGFlow）→ 容器内检索 401，全部拒答
  2. **kind 集群内没有 `host.docker.internal`** → RAGFlow/Ollama/Prometheus 全部解析失败（`docker-compose.yml` 的 `extra_hosts` 对 kind 不适用）
  3. **镜像 `fiscal-qa:1.0.0` / `fiscal-alert:1.0.0` 从未构建，仓库也没有构建脚本** → `ImagePullBackOff`
- **修复**：补 Secret 注入 key；kind 用 `extraHosts` 或宿主机桥接 IP；补 `scripts/build_images.ps1` + `kind load docker-image`。

### B5. 微调脚本在 README 声明的依赖范围内启动即崩
- **文件**：`finetune/train_lora.py:102`（`warmup_ratio=0.1`）、`:109`（`optim='paged_adamw_8bit'`）
- **实测证据**：本机 `transformers 5.15.1` 的 `TrainingArguments.__init__` **已无 `warmup_ratio` 参数**（实测 `has warmup_ratio: False`）→ 构造即 `TypeError`
- **二次阻断**：`paged_adamw_8bit` 需要 bitsandbytes，而 README 明确写"不用 QLoRA（bnb 对 Blackwell 不稳）"自相矛盾；GPU 分支创建 optimizer 就失败
- **影响**：微调这条线**完全跑不起来**，与"方案已就绪、换机器可跑"的宣称不符
- **修复**：`warmup_ratio` → `warmup_steps`；`paged_adamw_8bit` → `adamw_torch`；`transformers` 加上界（`<5`）。

### B6. 数据构造脚本零校验：知识库解析失败也"成功"产出
- **文件**：`finetune/build_dataset.py:78,88-93`
- **证据**：`parse_kb` 命中 0 条时仅 `print`，随后仍写出 9 条纯拒答训练集（`len(items)==0` 时 `train` 只有拒答样本），退出码 0
- **影响**：数据集悄悄变成"只会拒答"的坏数据，训练结果不可用却无任何报错
- **修复**：`assert len(items) >= 50`，否则非 0 退出；同时校验 `len(train) > 0 and len(dev) > 0`。

### B7. Dify 应用是"假通"：知识库从未真正参与检索 ⚠️（推翻此前"Dify 跑通"的结论）
- **文件**：`scripts/bind_dify_dataset.py:46`、`scripts/setup_dify015_app.py:110-126`
- **证据链**（三重验证）：
  1. Dify 0.15.3 源码 `core/app/app_config/easy_ui_based_app/dataset/manager.py`：`if "enabled" not in dataset or not dataset["enabled"]: continue` —— **dataset 条目必须带 `enabled: True` 才会被启用**
  2. 数据库实查：`app_model_configs.dataset_configs` = `{"datasets": {"datasets": [{"dataset": {"id": "...", "name": "..."}}]}}` —— **没有 `enabled` 字段** → 运行时跳过该知识库
  3. 现象印证：Dify 回答的 `metadata` 里 `retriever_resources` 为 **0 条**；而"预留 30%/小微企业 60%"恰好写在 `prompts/system_prompt.md:7` 的示例里 → **答案来自提示词，不是检索**
- **附带问题**：`setup_dify015_app.py` 建应用时把 `model_config`/`dataset_configs` 一起 POST `/apps`，但 0.15.3 的该接口只接受 name/description/mode/icon*，**其余字段被静默丢弃**，脚本却打印 `[OK]`，制造"已配置"的假象
- **修复**：dataset 条目补 `"enabled": True`；建应用后必须单独调 `model-config`；`test_dify_app.py` 增加断言（`retriever_resources` 非空才算通过）。
- **影响**：Dify 线路的实际能力 = "用本地模型 + 提示词回答"，**RAG 部分没生效**。修好后需重新验证。**

### B8. 启动/导入脚本"报成功但没生效"
- **文件**：`scripts/start_all.ps1:23-44`、`scripts/import_kb.py:117-127,136-137`、`scripts/fix_prompt.py:24-35`
- **证据**：
  1. `start_all.ps1`：`Wait-Http ... | Out-Null` 丢弃返回的 `$false`，任一服务失败也必然打印"全部启动完成"，且无退出码
  2. `import_kb.py`：`glob.glob(f)` 用 CWD 相对路径，而普通路径拼 `ROOT` —— 按 docstring 在 `scripts/` 下用 `--files ../data/...` 会得到 0 个文件；解析失败（run=FAIL）不计 done 也不计 running，循环满 900s 后返回 `[]`，main 仍打印"解析完成: 0 个文档"并继续冒烟检索
  3. `fix_prompt.py`：RAGFlow 实际读 `prompt_config["system"]`，脚本却把含 `{knowledge}` 的模板写进 `prompt` 键 → 补模板无效；SQL 拼接未转义反斜杠，JSON 可能损坏
- **修复**：start_all 收集结果并 `exit 1`；import_kb 先 `os.path.join(ROOT, f)` 再 glob、FAIL 立即退出；fix_prompt 改写 `system` 键并回读校验（该脚本已被自研编排取代，建议直接删除）。
